# Retrospective — STUDIO-12 (real chain anchoring on 40204)

## The Numbers

| Metric | Value |
|---|---|
| Anchor | audit root `0x50d89f48…` → tx `0xb89dde7e…`, **block 497881**, chain 40204 |
| Verification | `eth_getTransactionByHash` — the tx calldata **is** the root |
| Funding | `faucet.citrate.ai` → 10 SALT; anchor cost ~0.0000007 SALT |
| Key | secp256k1, address `0x6e5d…1929`, derivation verified vs the runtime's known vector |
| Builds | default 35 / core-live, both zero studio warnings |

## What Went Well

**1. The last gated item turned out to be a faucet call away.** "Anchoring needs a funded
signer + gas" had been marked 🔒 for sprints. It took one `POST /faucet` to fund the key and
one real transaction to anchor. The thing that *looked* like external infra was actually
self-serve. Worth checking what "gated" really means before deferring it.

**2. The runtime's `RecorderClient` did the hard part.** secp256k1 signing, EIP-155 tx
construction, nonce fetch, broadcast, receipt polling — all in agent-core, all tested there.
Studio's anchor is ~40 lines: build the client, compute the root (`AuditChain::last_hash`),
`send_tx_and_wait`. The seam pattern paid off one more time.

**3. Verified the address before spending.** I derived the key's EVM address and checked it
against the runtime's committed test vector (`0x4250…00c6`) *before* asking for funds or
sending anything. A keccak/curve mistake would have sent SALT to an unspendable address;
matching the known vector first ruled that out.

## What Didn't Go Well

**1. The "proper" contract anchor wasn't usable.** The deployed `AgentDecisionRegistry` has a
real `anchor(...)` method, but its writes are recorder-gated — a fresh, non-rostered key
would revert (and burn gas doing it). So the anchor is a **self-tx with the root in
calldata**, not a contract call. It's a real, readable, tamper-evident on-chain anchor, but
it's the authorization-free version. A rostered key (the deployer authorizing this address as
a recorder) could use the contract method; that's a permissioning step outside studio.

**2. The anchor is blocking (a few seconds).** `block_on(send_tx_and_wait)` parks for the
receipt. I ran it off-thread so the UI doesn't freeze, but a real product would want progress
feedback (submitted → mined) rather than a single "anchoring…" → result. Noted.

**3. A live private key now exists in the working tree.** It's in a gitignored
`.anchor-key.env` and holds ~10 SALT of testnet funds — low stakes — but it's a real secret
on disk. Production would put it in the OS keyring (the `KeyringTokenStore` pattern is right
there). Acceptable for a funded testnet demo; flagged so it isn't mistaken for a pattern to
ship.

## Honest Assessment

**Strong:** the trust chain is now complete end-to-end and *on a real chain* — a real key
signs a real attestation through the real queue, gating a real capsule that runs on real
wasmtime, recorded in a real audit chain whose root is anchored in a real transaction on
chain 40204. Every link is real, and the last one is publicly verifiable.

**Needs work:** contract-method anchoring (needs recorder authorization), progress UX, and
keyring storage for the anchor key in production.

## The Partnership Dynamic

Larry offered to fund an address via the deployer *or* point me at the faucet — and the
faucet turned out to be all it took. The right move was to derive + verify the address, fund
it self-serve, anchor for real, and verify the result on-chain *before* declaring it done —
so "anchoring works" is a transaction hash anyone can look up, not a claim. The whole project
has run on that standard; the anchor is its most literal expression: a fact on a public
ledger.
