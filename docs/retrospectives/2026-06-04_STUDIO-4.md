# Retrospective — STUDIO-4 (signer roster + real ed25519 key enrollment)

## The Numbers

| Metric | Value |
|---|---|
| New tests | 7 (keypair roundtrip, signer_id vector, enroll+fail-closed, PIV stub, persist roundtrip, save/load, dock real-signature) — 24 total |
| New dep | `ed25519-dalek` 2.1 (the runtime's native scheme) |
| Signing surfaces | FileBacked + Keyring working; PIV/CAC + FIDO2 stubbed behind a typed seam |
| Default build | zero warnings |
| Demo roster | 5 real generated keypairs; dock fp + Settings signer_id are real SHA-256(pubkey) |

## What Went Well

**1. "Real" went all the way down.** The dock fingerprints are no longer
decorative strings — they're `SHA-256(pubkey)` of freshly generated ed25519 keys,
and pressing Sign produces an actual signature over the capsule's payload hash that
is **verified before it counts**. The same `signer_id` shows in the dock, the
Settings roster, and (when wired) the core's `SignerRoster`. There's one identity,
computed one way.

**2. The surface tiers are honest about what's real.** FileBacked and Keyring sign
for real; PIV/CAC and FIDO2 return `SignError::SurfaceNotWired` — a typed seam, not a
silent fake. A reviewer can see exactly where the hardware-attestation work picks up,
and a test (`piv_surface_is_stubbed_not_faked`) pins that it errors rather than
pretends.

**3. Fail-closed is visible, not just asserted.** Disenroll a role and its dock row
goes disabled with "No signer enrolled (fail-closed)"; the gate cannot be satisfied.
The planset's security truth ("no roster ⇒ High/Critical can't be approved") is now
something you can *see happen* in the UI, backed by a test.

**4. Seeding kept the demo alive.** Rather than start with an empty roster (correct
but a dead demo), first run seeds the five demo signers with real generated keys and
persists them — so the existing approval flow immediately runs on real crypto, and
enroll/disenroll edits a live, persisted roster.

## What Didn't Go Well

**1. FileBacked stores a private key in a plaintext JSON file.** That's the dev
surface, clearly named, and the seeded demo uses it so the app works out of the box —
but a private key on disk is a real risk if anyone mistakes FileBacked for a shipping
default. **Mitigation in place**: Keyring is one click away in Settings and stores the
secret in the OS keyring instead; the file then holds only the pubkey. **Action**: when
STUDIO-5 lands the persistent config, default new enrollments to Keyring and mark
FileBacked dev-only in the UI copy, not just the code comment.

**2. The signature is produced and verified, but not yet *consumed* by the core.**
STUDIO-4 proves a real attestation can be made; the real async `ApprovalQueue` that
verifies attestations against pinned payloads is STUDIO-6. So today the signature is
verified locally and then the *quorum decision* still runs through the policy seam —
the signature's existence isn't yet what advances the gate. That's the right seam
(STUDIO-3 owns the decision, STUDIO-6 owns the queue), but it means "real signature
satisfies the gate" is true in-memory, not yet through the runtime's verifier.

**3. Tests touch the real user config dir via `new_state()`.** `load_or_seed()` reads
the platform config path, so tests that build a `RunState` depend on (or create) a
real `roster.json`. The crypto/roster tests are isolated (seed_demo + temp files), but
the dock test had to override `s.roster` explicitly to be deterministic. **Lesson**: a
state constructor that does I/O is a testability smell — a future cleanup should let
`new_state` take an injected roster (or a config path) so nothing reads `$HOME` in a
unit test.

## Honest Assessment of Where We Are

**Strong:**
- Real ed25519 identities, end to end: generated, enrolled, persisted, signed, verified,
  with the same `signer_id` everywhere — and fail-closed you can watch.
- A clean surface-tier seam that's truthful about FileBacked/Keyring (real) vs
  PIV/FIDO2 (stubbed).

**Needs work:**
- The signature isn't consumed by the real verifier yet (STUDIO-6).
- FileBacked-by-default and the config-dir I/O in `new_state` are debts to pay in
  STUDIO-5.

## The Partnership Dynamic This Sprint

A clean "start STUDIO-4 → run to the gate" hand-off. The judgment calls — seed real keys
so the demo lives, make FileBacked the bootstrap surface but put Keyring one click away,
keep the *decision* in the policy seam and defer the *queue* to STUDIO-6 — were mine, and
each is written down here and in the sprint so the next session (and the audit) inherits
the reasoning, not just the diff. Same pattern that's held since the STUDIO-2/3 gates: the
method makes the honest engineering call the cheap one.
