# Retrospective — STUDIO-13 (UI-kit extraction)

## The Numbers

| Metric | Value |
|---|---|
| Extracted | theme + typography + icons + primitives (23 components) + 4 fonts → `ui-kit/` |
| Consumers | Studio (via re-export shims) **and** `examples/kit-gallery` (a second shell) |
| Studio import churn | **zero** — every component import unchanged |
| Proof | `visual-harness.sh check` — all 19 surfaces **pixel-identical** to baseline |
| Builds | studio + gallery + core-live, zero warnings; 35 tests |

## What Went Well

**1. The re-export shim meant zero churn in the consumer.** Moving four `.slint` files out
of Studio could have meant rewriting every `import { Theme } from "theme.slint"` across dozens
of components. Instead, Studio's `theme.slint` (etc.) became a one-line shim —
`export { Theme, Settings } from "@citrate-ui-kit";` — so every existing import resolves
through the shim into the kit. The definitions moved; the import surface didn't.

**2. The visual harness was the safety net I'd built two sprints earlier.** A design-system
extraction is exactly the change that can silently shift a pixel. STUDIO-11's golden images
turned "I think it's identical" into "the gate confirms all 19 surfaces are pixel-identical."
That's the difference between hoping a refactor is behavior-preserving and proving it.

**3. The federation had a pattern to follow.** gui-native's `citrate-ui-kit` (the
`links` + `DEP_…_UI_KIT` + `@library` mechanism) was the template. I didn't invent the
cross-crate Slint approach; I matched the proven one, at the version Studio needs.

## What Didn't Go Well

**1. The `DEP_…_UI_KIT` env didn't propagate to the build-dependency's script.** The proven
pattern publishes the kit's path via `links` and reads it in the consumer's `build.rs` as
`DEP_CITRATE_STUDIO_UI_KIT_UI_KIT` — but that env var wasn't set (the panic at `build.rs:9`
proved it). Rather than chase the cargo-metadata propagation rule, I used a workspace-relative
fallback (`ui-kit/ui/lib.slint`), preferring the DEP env when present. It works, but it means
the link is a *path* relationship today, not the full git-dep-friendly metadata one. A
follow-up could pin down why the metadata didn't surface (build-dep vs normal-dep, cargo
version) and rely on it.

**2. The kit became a pure asset crate, not a Rust-types crate.** Compiling the kit's own
components for `use citrate_studio_ui_kit::Btn;` produced "doesn't inherit Window — no code
generated" warnings for every primitive (expected: they're sub-components, used via the
library import). Rather than carry those warnings, I dropped the Rust-side compile — the kit
ships `.slint` + fonts + the path, and consumers generate their own types. Clean and correct
for this use, but a pure-Rust consumer (no `.slint` of its own) can't `use` the kit's types.
That's a fine trade for a Slint-first design system.

**3. Two kits now exist in the federation.** gui-native's is Slint 1.9; this one is 1.16.
Studio's is the forward-looking one (per the planset), but the federation carries two UI-kit
crates until gui-native migrates to 1.16. Documented, not hidden — a future consolidation,
not a surprise.

## Honest Assessment

**Strong:** the design system is a real shared crate, consumed by two shells, with the
extraction proven pixel-identical and zero import churn in the main app.

**Needs work:** the DEP-metadata link (vs the relative-path fallback); kit Rust types for
non-Slint consumers; eventual consolidation with gui-native's 1.9 kit.

## The Partnership Dynamic

Larry queued three sprints in order — kit, installers, audit — and trusted the planset for
each. The kit extraction was the riskiest of the three (a design-system move can break a green
build subtly), and the right move was to lean on the safety net the project had already built:
make the change, run the golden-image gate, and let "all 19 surfaces match baseline" be the
sign-off. The earlier sprint paid for this one.
